# Item Actions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an item carry rules the character *does* — so a vial of acid rolls its attack from the inventory row — and give every rule the engine cannot enforce a declared way to reach the player.

**Architecture:** `EquipmentDefinitionSchema` gains an `actions` array, which reaches the engine through the existing `itemRule` projection. `CharacterEngine` gathers those from carried inventory into an `itemActions` list kept deliberately apart from `liveSheet.actions`, so the combat list is unchanged. Item use routes through the existing `ActionResolver` under `economyPolicy: "track"`. Rules the engine cannot run are declared by using the `no_effect` effect type, and are carried to the player as a `tableNote` lifted off `AttackEffectSchema` onto the action itself.

**Tech Stack:** TypeScript, Zod 4, Vitest, pnpm workspaces, Drizzle, socket.io, React + Zustand.

**Spec:** `docs/superpowers/specs/2026-09-01-item-actions-design.md`

## Global Constraints

- **Line endings: every source and pack file in this repo is CRLF on disk**, except `packages/database/data/schemas/*.schema.json` which `.gitattributes` pins to LF. `git config core.autocrlf` is `true`. Read with `readFileSync(p, "utf8")`, edit, and write back in the file's original ending. `pnpm check:hygiene` gates this for `apps/` and `packages/`.
- **Never hand-edit `packages/database/data/schemas/*.schema.json`.** They are generated by `pnpm --filter @project/database schemas:generate` from the Zod schemas. `packSchemas.test.ts` byte-compares regeneration and will fail otherwise.
- **Typecheck all five packages, never through turbo** — turbo caches `typecheck` and replays stale successes. Run `npx tsc --noEmit` inside `packages/shared`, `packages/database`, `packages/engine` and `apps/server`, and `npx tsc -b` inside `apps/web` (a bare `--noEmit` there checks zero files). **Checking only the package you edited is not enough:** a schema change ripples into every package that constructs a literal of that type, and vitest does not typecheck, so a fully green suite proves nothing about this.
- **Baseline is green: 1714 tests, 0 failures.** shared 191, database 147, engine 771, server 320, web 285. A failure is yours.
- **`z.toJSONSchema` silently drops `.refine()`.** Any refine added here is Zod-only and must be covered by a direct unit test, as `equipment.test.ts` already does for `WeaponCapabilitySchema`.
- **Commit after every task.** Work directly on `main`.

## Task 1: Lift `specialNote` onto the action as `tableNote`

**Files:**
- Modify: `packages/shared/src/schemas/content/actions.ts:165` (remove `specialNote` from `AttackEffectSchema`), `:207-220` (`ActionGrantSchema`)
- Test: `packages/shared/src/schemas/__tests__/actions.test.ts`

**Interfaces:**
- Consumes: nothing.
- Produces: `ActionGrantSchema` with `tableNote?: string`, refined so a `no_effect` action must carry one. `AttackEffectSchema` no longer accepts `specialNote`.

**No schema-level note requirement.** An earlier draft refined `ActionGrantSchema` so a `no_effect` action had to carry a `tableNote`. That is false of actions in general: 5 standard actions (Disengage, Help, Ready, Search, Use an Object) and 111 `unimplemented` spell stubs are `no_effect` with no note, and rightly so. The rule is true of *item* actions only, so Task 9 enforces it against item data instead.

**Why removing specialNote is safe:** `specialNote` is authored in the shipped pack on exactly two weapon blocks (lance, net) under `weapon.specialNote`, which is `WeaponCapabilitySchema` and is **not** changing. It appears zero times inside an authored action or effect. `ActionGrantSchema` is only ever `.parse`d — nothing calls `.extend()` or `.shape` on it — so wrapping it in `.refine()` breaks no caller.

export interface ActionIntentPayload {
  characterId: string;
  requestId: string;
  actionId: string;
  /**
   * Where the action was found.
   *
   * "item" resolves against the character's itemActions rather than the live
   * sheet's action list, because item actions are deliberately kept out of the
   * combat list - they are used from the inventory row.
   */

- [ ] **Step 5: Build a server-side inventory ledger**

**The server has never had one.** `inventoryLedger` appears only inside the engine and in the web layer's adapter; `socket.ts` has never passed one, so `consumesSelf` would fail `no_ledger` on every call. This step creates it.

The interface is **synchronous** (`consumeStack(id, amount): void`) and the database is not, so the ledger buffers deductions in memory and they are flushed after `execute` returns. That is safe for exactly the reason `InventoryLedger` documents: the resolver settles every unpredictable cost before touching inventory, so a deduction is always last and never has to be unwound.

Create `apps/server/src/services/inventoryLedgerService.ts`:

```ts
import { and, eq, sql } from "drizzle-orm";
import type { InventoryLedger } from "@project/engine";
import { db, characterInventory } from "@project/database";

export interface BufferedInventoryLedger extends InventoryLedger {
  /** Deductions taken during resolution, in the order they were taken. */
  readonly pending: ReadonlyArray<{ id: string; amount: number }>;
}

/**
 * A ledger over rows already read for this resolution.
 *
 * Reads are served from the snapshot the caller fetched, so the resolver never
 * awaits mid-settlement; writes are buffered and flushed afterwards by
 * `flushInventoryLedger`. Splitting it this way is what lets a synchronous
 * engine port sit on top of an asynchronous store.
 */
export const buildInventoryLedger = (
  rows: Array<{ id: string; itemId: string; quantity: number }>,
): BufferedInventoryLedger => {
  const byId = new Map(rows.map((row) => [row.id, { ...row }]));
  const pending: Array<{ id: string; amount: number }> = [];

  return {
    pending,
    getStack: (instanceId) => byId.get(instanceId),
    consumeStack: (instanceId, amount) => {
      const stack = byId.get(instanceId);
      if (!stack) return;
      stack.quantity -= amount;
      pending.push({ id: instanceId, amount });
    },
  };
};

/**
 * Persists what the resolver spent.
 *
 * Mirrors the ITEM_CONSUMED handler exactly - a stack that reaches zero is
 * swept rather than left as a zero row - so the two paths cannot drift into
 * disagreeing about what an empty stack is.
 */
export const flushInventoryLedger = async (
  characterId: string,
  ledger: BufferedInventoryLedger,
): Promise<void> => {
  if (ledger.pending.length === 0) return;

  await db.transaction(async (tx) => {
    for (const deduction of ledger.pending) {
      const [row] = await tx
        .select({ quantity: characterInventory.quantity })
        .from(characterInventory)
        .where(
          and(
            eq(characterInventory.id, deduction.id),
            eq(characterInventory.characterId, characterId),
          ),
        );

      if (!row) continue;

      if (row.quantity - deduction.amount <= 0) {
        await tx
          .delete(characterInventory)
          .where(eq(characterInventory.id, deduction.id));
        continue;
      }

      await tx
        .update(characterInventory)
        .set({
          quantity: sql`${characterInventory.quantity} - ${deduction.amount}`,
        })
        .where(eq(characterInventory.id, deduction.id));
    }
  });
};
```

Adjust the `db` / `characterInventory` import to match how `socket.ts` already imports them.
