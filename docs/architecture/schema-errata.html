Schema Errata

Two schema systems describe the same rulebook. The Zod side is correct but unlayered; the JSON side is layered after the Zod side and is simply wrong — and nothing loads it, so it has never once said so.

12 / 30 pack segments fail their own JSON schema
0 files that load the JSON schemas
3× schemas for one equipment concept
7× places an ability score is defined
Verdict

The two halves have opposite problems

Your instinct is right, but the two halves are not sick in the same way, and reorganising them together would repeat the mistake that produced the drift.

The Zod schemas are load-bearing and correct. The core pack assembles, validates, and 84 database tests pass. What is wrong there is structural: 22 files sit flat in one directory with no separation between authored content, engine runtime state, and wire payloads, so a single concept is defined in whichever file first needed it — and then again in the next.

The JSON schemas are inert and factually wrong. No pack file declares a $schema, no TypeScript imports them, no test asserts them. I validated the real pack against them with ajv and 12 of 30 segments fail — every failure is a defect in the JSON schema, not the data. They have been silently rotting since they were written, because hand-mirroring a schema is a job with no feedback loop.

The load-bearing conclusion

Do not reorganise the JSON schemas by hand. Every one of the six drift classes below exists because a human had to remember to mirror a Zod change. Generate them from the Zod authored-content layer instead, and the mirroring problem stops existing. That reframes the refactor: the JSON layout is an output, so the only structural decision that matters is how the Zod side is layered.

The structural fault underneath all of it

Individually these are typos. Together they say something sharper: the JSON schemas were organised by mirroring the Zod filenames, which is the wrong organising principle, because the Zod filenames are not organised around what a pack author writes.

Three symptoms of that single mistake:

  • The file names lie about which shape they hold. spells.schema.json models the trait-embedded grant block, but corePackSegment wires it to the pack's spells array, which is a spell definition — a completely different object. Same mistake in resources.schema.json. Both pass anyway, because neither sets additionalProperties: false or any required that bites, so they validate vacuously.
  • They model no consistent layer. traits.schema.json includes isStartingProficiency, so it models CoreTraitSchema. equipment.schema.json omits lore, isBundle, bundleContents and implementation, so it models the base EquipmentDefinitionSchema. A pack author cannot tell which layer they are writing against.
  • common.schema.json is a grab-bag, not a layer. It holds equipmentType, armorCategory, equipSlot and startingEquipmentCategoryTag — all equipment concepts — while weaponCategory lives in weapons and damageType in affinities. It also holds creatureSize while creatureType lives elsewhere. "Common" here means "whatever needed two referrers first".

corePackSegment.schema.json itself declares classes, subclasses, feats and backgrounds as bare {"type": "array"}, and omits proficiencies entirely. Roughly half the pack has no schema at all.

The Zod schemas: correct, and completely unlayered

This is where your "concepts spread throughout the files" instinct is exactly right — and it is worse than scatter. Several concepts are not merely spread, they are independently redefined, with the copies already drifted apart.

Live consequence of the name collision

index.ts star-exports resources.js and named-exports ResourceMaxRuleSchema from rules.js. An explicit export beats a star export, so ResourceMaxRule from @project/shared is always the three-kind version and resources.ts's two-kind version is unreachable through the barrel.

The visible result: ResourceManager.resolveMaxCharges handles total_level_thresholds, but it is only ever called with a ResourceGrant.maxRule, whose union does not contain that member. An author who writes it on a trait gets a parse error from a schema sitting next to a calculator that looks like it supports them. The barrel already carries a hand-written comment explaining the collision — a note where a fix belongs.

Concepts filed under the wrong heading

  • TargetFilterSchema lives in creatures.ts. It is an action targeting concept that happens to reference creature types — which is why actions.ts imports creatures.ts to get it.
  • DamageTypeSchema lives in affinities.ts. Damage type is a primitive of the whole rules system; weapons, actions and dice all reach into the resistance module to get it.
  • dice.ts imports AttackTypeSchema from actions.ts and scaling from modifiers.ts, then re-declares the four scaling fields by hand with a comment explaining they are copied to match. Three modules to express one critical-hit rule.
  • rules.ts is a junk drawer: it re-exports weapons, redefines resources and traits, and holds RuleSnapshot. It is the single reason the barrel needs a hand-maintained exception list.
  • coreRulePack.ts is 680 lines doing three jobs — schema definitions, a ~350-line hand-written semantic validator, and the toRuleSnapshot projection. The validator is good code in the wrong file.

The missing axis

Underneath every one of these is one absence: nothing in the directory records whether a schema describes authored content, live runtime state, or a wire payload. All three are mixed inside single files. items.ts holds ItemDefinition (authored) beside InventoryInstance (runtime). modifiers.ts holds BaseModifier (authored) beside RuntimeModifier (runtime) beside a CalculationResult interface that is neither. character.ts holds ClassDefinition (authored), CharacterSave (runtime) and CreateCharacterPayload (transport).

That is the thing to fix. It also answers your engine-vs-data question — but the split you guessed at is one axis short.

Part C

What I would do instead

Split on three axes, not two

"Engine vs data" is the right instinct but collapses two different things into "engine". A RuntimeModifier and a socket payload are both non-authored, but they change for opposite reasons: one changes when the rules engine changes, the other when the wire format does. Four layers, each importing only downward:

The layering is not bureaucracy — it answers real questions that are currently unanswerable. Where does InventoryInstance go? Runtime; it never appears in a pack. ItemDefinition? It disappears — see below. Does the wire format changing force a pack version bump? Only if content/ changed, which the directory now tells you.

Two collapses this makes obvious

ItemDefinition and WeaponDefinition should not survive the move. EquipmentDefinition is already the authored source and already carries every field of both; equipmentProjection.ts exists purely to convert between them. Once content/equipment.ts is the single authored shape, the two legacy types become runtime projections at most — and the tool/loot enum members either get authored properly or get deleted.

TraitEffect and TraitDefinition need to be reconciled, not relocated. Homebrew and import payloads speak TraitEffect; packs speak TraitDefinition. That is a genuine product problem hiding as a schema problem — homebrew content cannot express what core content can. Worth deciding deliberately rather than carrying both into the new layout.

Generate the JSON schemas; never write them

Once content/ exists, zod-to-json-schema over the pack envelope emits one pack.schema.json as a build step. That single change:

  • Kills all six drift classes permanently — the mirror cannot lag a source it is derived from.
  • Covers classes, subclasses, feats, backgrounds and proficiencies, which have no schema today, for free.
  • Ends the "which layer is this modelling" ambiguity — it models the layer it was generated from, by construction.
  • Gives pack authors real editor autocomplete the moment a "$schema" key is added to the segment files. None of the 32 pack files has one today, which is why nobody noticed the schemas were broken.
  • Turns drift into a CI failure: regenerate, then git diff --exit-code.

What generation cannot carry is the cross-reference checking — unknown trait ids, ammunition compatibility, progression ordering. That is what validateCoreRulePack already does well, and giving it its own file in content/ makes the division of labour explicit: JSON Schema for shape, the validator for meaning.

Sequence

Ordered so each step is independently shippable and the highest-risk items land while the test suite is green.

  1. Delete the JSON schemas

    All 15. They validate nothing, they are wrong in six verified ways, and keeping them through the refactor means porting bugs. This is reversible in one git revert and removes the temptation to hand-fix them.

  2. Resolve the two hard collisions first

    Pick one ResourceMaxRule and one ResourceReset (the union of both enums looks right), collapse ResourceGrant and ResourceRule into one schema, and delete the minimal TraitDefinitionSchema from rules.ts. The barrel's exception list then disappears, which is the signal it worked.

  3. Extract primitives/

    Pure moves with re-exports left behind, so nothing downstream breaks. The ability score and state predicate are the highest-value two — they touch the most files and have already drifted.

  4. Split content/, runtime/, transport/

    Mechanical once primitives exist. Break coreRulePack.ts into its three jobs here. Keep index.ts flat-exporting everything so no consumer changes in this step.

  5. Generate pack.schema.json and wire it up

    Build step, "$schema" key in all 32 segment files, and the git diff --exit-code check in CI. The pack becomes self-describing for the first time.

  6. Retire ItemDefinition and WeaponDefinition

    Last, because it touches close to 100 non-test references. Safe to defer indefinitely — the layering delivers most of its value without it.
